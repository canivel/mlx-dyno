MLX Dyno

Put your model on the dyno.

An MLX inference server for Apple Silicon that reports what it is actually doing — tokens per second, time to first token, prefill throughput and prompt-cache hits — plus a native menu bar app that shows those beside the machine's own GPU, power and memory telemetry.

Apple Silicon no sudo OpenAI-compatible Prometheus /metrics MIT

Install

# the server + CLI
$ uv venv ~/.mlx-dyno/venv
$ uv pip install --python ~/.mlx-dyno/venv/bin/python 'mlx-dyno[serve]'

# the menu bar app
$ git clone https://github.com/canivel/mlx-dyno && cd mlx-dyno/app
$ ./build.sh && cp -r build/Dyno.app /Applications/

The app finds the CLI automatically, so that install path needs no configuration.

$ dyno serve --model mlx-community/Qwen3-8B-4bit --port 8971

Every mlx_lm.server flag still works, because this is not a fork. It imports mlx_lm.server, swaps two classes for instrumented subclasses, and hands control back — so batching, prompt caching and speculative decoding all come along unchanged. The additions are timing hooks inside the token stream and two endpoints.

Why this exists

Running a large model locally on a Mac is mostly a memory problem, and the tools do not show you memory the way it matters.

There is no nvidia-smi on macOS. Activity Monitor reports a GPU percentage that cannot tell a GPU pinned at a low clock apart from one doing real work, and reports memory used without reference to the only ceiling that counts: how much unified memory Metal will actually let the GPU hold. On a 128 GB machine that is 107.5 GB, not 128. Cross it and allocations quietly spill back to CPU memory, throughput falls off a cliff, and nothing tells you why.

Then there is throughput itself. Token generation is memory-bound — every token re-reads the entire weight set — so tokens per second is set by bandwidth, not by GPU utilisation. A GPU reading 99% busy while pulling 250 GB/s and one pulling 400 GB/s are different machines having very different days.

llama.cpp and vLLM both publish Prometheus metrics, so anyone can read their real throughput. On Apple Silicon the fast path is MLX — and mlx_lm computes throughput internally on every single request, then discards it. Anything watching from outside has to infer it.

You can infer it, up to a point. Read bandwidth divided by weight-set size gives the decode rate. On a 27B 8-bit model on an M5 Max that predicted 8.97 tok/s against 8.70 measured — within 3%. But the moment a second request shared the GPU, the same estimate read ~10.3 against 8.73 actual.

Excellent in isolation, 18% high under load. Fine for a dashboard glance; not something to benchmark against, tune a batch size with, or pick a quantisation level on.

So expose the number instead of guessing it. The measurement happens inside the token stream, where it is simply a fact rather than an inference.

What it measures

MetricMeaning
mlx:decode_tokens_per_secondIn-flight throughput; falls back to recent history when idle
mlx:live_decode_tokens_per_secondRequests generating right now, summed
mlx:last_time_to_first_token_secondsPrompt processing plus queue wait
mlx:last_prompt_tokens_per_secondPrefill throughput
mlx:cached_prompt_tokens_totalPrompt tokens the cache served
mlx:tokens_generated_totalCumulative counter
mlx:requests_activeGenerating or queued right now
mlx:memory_active_bytesMLX allocator, plus peak and cache

The decode rate deliberately excludes prompt processing and queue time: tokens produced divided by the time spent producing them. Verified against wall-clock timing — a request taking 5.46 s end-to-end with 0.36 s to first token reported 31.2 tok/s, exactly 159 ÷ 5.10.

/stats returns the same figures as JSON, plus the last ten requests individually.

No sudo, ever

Most Apple Silicon monitors shell out to powermetrics, which needs root. This reads the same counters one level down through IOReport, IOKit and Metal.

The real memory ceiling

GPU memory is shown against Metal's recommendedMaxWorkingSetSize — the actual limit for weights plus KV cache, not total RAM.

Bandwidth, not just utilisation

DRAM read and write throughput, because that is what predicts tokens per second on a unified-memory machine.

Other runtimes too

llama.cpp, vLLM, Ollama and LM Studio are detected by the ports they listen on, with measured throughput wherever they report it.

The app

A native Swift menu bar app — no Python, no Dock icon, no window to manage. It shows live tokens/sec in the menu bar, starts and supervises model servers, and stops them when you quit so a model is never left holding tens of gigabytes.

Idle cost: about 3% of one core and a flat 80 MB.
